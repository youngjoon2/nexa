## 버전 지식베이스 검증

이번 변경은 프로젝트·자료 역할·모듈 규칙, 원격 Git 및 문서 폴더 동기화, 확정 버전의 원문 보존, 공유 파싱·임베딩 캐시, 기능 분석과 버전 사양 비교를 대상으로 검증했습니다.

`tests/version-live-smoke.ts`를 실행 중인 llama.cpp 생성·임베딩 서버와 Qdrant에 연결해 실행했습니다. 임시 SQLite·원문 디렉터리와 고유 Qdrant 컬렉션을 만들고 종료 시 정리했습니다. 기본 자료 컬렉션에는 테스트 버전을 추가하지 않았습니다. 최종 코드의 전체 검증 시간은 **21.46초**였으며, 개별 질문 지연이나 동시 사용자 성능을 의미하지 않습니다. 로컬 결과는 `.test-data/version-live-results.json`에 저장했습니다.

| --- | --- |
| v1.0 / v2.0 UART 속도 질문 | 각각 115200 / 230400 bps와 해당 버전 인용 |
| TRACE_EXPORT 기능의 버전별 조사 | v1.0 사양·빌드 미지원 및 코드 미확인, v2.0 사양·코드·빌드 포함 근거, v3.0 사양·코드 존재 및 명시적 빌드 제외 |

브라우저는 별도 임시 데이터와 8877 포트의 키워드 모드로 검증했습니다. 프로젝트 생성, 폴더 연결, 갱신, A/B 버전 확정, 비교 작업 완료와 원문 인용 열기를 확인했습니다. 원본이 921600으로 바뀐 뒤에도 A의 인용은 115200을 표시했습니다. 프로젝트 선택은 새로고침 뒤 유지되며, 비교 결과 화면을 시각적으로 확인했습니다. 이 실행에서 브라우저 콘솔 오류·경고는 0개였습니다.

실제 Pandoc 3.11 및 MinGit 2.55.0.5로 DOCX와 Git fixture 테스트를 수행했습니다. 원격 인증은 모의 명령 검사와 로컬 Git fixture로 검증했으며 실제 사내 비공개 GitHub·Bitbucket 저장소의 인증은 검증하지 않았습니다.

모델 검증 과정에서 일반 함수가 빌드 포함 근거로 섞이거나 질문의 식별자와 무관한 함수가 구현 근거로 채택되는 사례를 발견했습니다. 코드·빌드 후보를 분리하고 명시적 식별자의 후보·인용문 경계를 검사한 뒤 재검증했습니다. 관련 회귀 테스트와 최종 실제 모델 검증이 통과했습니다. 일반 자연어 질문의 의미 판정 정확도는 별도 실무 정답 세트로 평가해야 합니다.

2026-09-22 00:04에 기본 로컬 서비스를 새 코드로 재시작했습니다. `data/backups/before-knowledge-1790003043167.sqlite` 백업이 생성됐고 기존 소스 2개·문서 5개·청크 6개를 유지했습니다. 생성·임베딩·Qdrant 연결이 모두 정상이며 색인·분석 대기열과 미처리 임베딩은 0개였습니다. 재시작 후 실제 브라우저에서 ATLAS / A의 UART 속도를 질문해 115200과 올바른 원문 인용을 확인했습니다. 브라우저 오류·경고와 API 오류 로그는 없었습니다.

## 합성 자료 규모 검증

`tests/scale-smoke.ts --run`은 기존 자료를 열지 않고 OS 임시 디렉터리에 50개 버전 × 버전당 10,000개 파일 항목을 생성했습니다. 각 버전은 9,500개 내용을 공유하고 500개는 버전 고유 내용으로 구성했습니다.

| 항목 | 결과 |
| --- | --- |
| 보존 버전 / 파일 출현 항목 | 50개 / 500,000개 |
| 고유 원문 / 파싱 결과 / FTS 청크 | 각각 34,500개 |
| 논리적 원문 바이트 | 공유 전 44,658,390 → 공유 후 3,283,280바이트 |
| SQLite 파일 | 367,865,856바이트 |
| 합성 자료 생성·스냅샷 저장 | 약 221.3초 |

모든 확정 버전이 최근 30개 정리 기준 이후에도 유지되고, 다른 버전의 결과가 섞이지 않음을 검증했습니다. 원문의 논리적 바이트 절감률은 약 92.65%이며, 파일시스템 할당량·SQLite 메타데이터·백업을 포함한 전체 디스크 절감률은 아닙니다.

최초 실행에서 선택적 키워드 질문 5개가 총 12.68초 걸려 SQL 실행 계획을 검사했습니다. FTS 후보마다 버전 범위의 10,000행을 반복 조회하던 경로를 `parsedKey` 인덱스 조회로 바꿨습니다. 기존 임시 DB를 읽기 전용으로 연 `tests/scale-query-smoke.ts`에서 같은 5개 동시 요청을 비교한 결과, **11,996.96ms → 212.16ms**로 줄었습니다. 반환된 25개 문서·청크 ID와 순서는 전후 동일했고, 실제 `KnowledgeBase.lexical` 결과도 일치했습니다. 새 인덱스나 테스트 DB 변경은 없었습니다.

```powershell
.\.runtime\bun\bun.exe --no-install tests/scale-smoke.ts --run
# 위 명령이 출력한 임시 scale.sqlite 경로 사용
.\.runtime\bun\bun.exe --no-install tests/scale-query-smoke.ts --run --db=C:\Users\사용자\AppData\Local\Temp\nexa-scale-smoke-XXXXXX\scale.sqlite
```

작은 합성 텍스트와 미리 만든 청크를 사용했습니다. Git 수집, DOCX/PDF 파싱, 임베딩, Qdrant, 모델 생성은 이 측정에 포함되지 않습니다. 5개 동시 loopback HTTP 요청은 하나의 프로세스와 동기 SQLite를 공유합니다. 이 결과를 실사용 5명의 전체 RAG 응답 성능이나 SLA로 해석하지 않습니다.

## 기존 RAG 실행 기록

`scripts/setup.ps1 -Offline`로 검증 캐시에서 설치하고 모델을 포함한 SHA256을 확인했습니다. `scripts/start.ps1`로 생성 모델, 임베딩 모델, Qdrant, API를 실행했습니다. 모델/API 경로는 모두 loopback이고 llama.cpp에는 `--offline`, Qdrant에는 telemetry 비활성화를 적용했습니다.

실제 RAG 검증은 5개의 가상 문서(Rev A 4개, Rev B 1개)와 6개의 질문으로 수행했습니다. Markdown뿐 아니라 C 코드의 함수·전처리 영역도 색인했습니다. 보드·리비전 필터를 요청에 명시했습니다.

| 질문 | 필터 | 실제 답변의 핵심 | 결과 |
| --- | --- | --- | --- |
| UART 콘솔 통신 속도 | ATLAS / A | 115200 | 통과 |
| UART 콘솔 통신 속도 | ATLAS / B | 921600 | 통과 |
| SPI 대기 시간 초과 오류 | ATLAS / A | -ETIMEDOUT | 통과 |
| 전원 레일 순서 | ATLAS / A | 1.8 V → 5 ms → 3.3 V | 통과 |
| 애플리케이션 플래시 시작 주소 | ATLAS / A | 0x00080000 | 통과 |
| 최대 동작 온도 | ATLAS / A | 자료에서 확인할 수 없습니다. | 통과 |

모든 질의는 하이브리드 검색 경로를 사용했고, 답변 가능한 항목은 실제 색인 문서의 인용을 반환했습니다. 최초 실행 및 재시작 후 실행의 답변 시간은 약 0.60~1.33초였습니다. 작은 예제의 단일 사용자 결과이며 대규모 자료나 동시 접속의 정확도·응답 시간 지표로 해석하지 않습니다.

## 자동 테스트

`bun --no-install test ./tests`로 Nexa 자체 테스트만 실행합니다.

기본 테스트는 실제 모델을 호출하지 않습니다. 등록 폴더 전체가 삭제된 뒤 오래된 최신 검색 결과가 제외되고 확정 버전은 유지되는 회귀 테스트를 포함합니다. 최종 실행 결과: **85개 통과, 실패 0개, assertion 776개**.

- UTF-8/UTF-16, 잘못된 인코딩, 바이너리, 크기 제한, AST 함수/선언, 한국어 청크, 실제 PDF 페이지 인용
- 폴더 탐색 제외·junction 차단·파일 수 제한 진단
- FTS5 식별자와 보드·리비전 필터
- 문서 교체 트랜잭션과 롤백, 삭제된 문서의 FTS·벡터 참조 차단
- 벡터 장애의 키워드 전환, 잘못된 근거 ID 거부, 근거 부족 처리
- 생성 요청 대기열 상한·순서·오류 이후 복구
- API 인증·자료 등록·증분 변경·삭제·업로드·출처 제한
- DOCX 제목·표·변경추적, Git 커밋 고정·태그·경로 검증
- 원본 수정·삭제·연결 해제 후 확정 버전 보존, 보존 원문 재색인
- 동일 내용의 버전별 출처 분리, 모듈·역할 변경과 과거 메타데이터 보존
- 버전·후보의 스냅샷 보존과 불필요한 자료 정리, 변경 없는 내용 재사용
- 기능 미확인·명시적 미지원·상충 근거 구분, 전체 사양 diff·숫자·표·양쪽 인용 검증
- 분석 작업 취소·재개, 일반 질문과 생성 대기열 공유
- 기존 DB 사전 백업, 과거 추출 텍스트 표시, 실제 원문으로 재동기화

실제 모델 smoke 테스트는 기본 테스트와 분리했습니다. 기존 `tests/live-smoke.ts`는 실행 중인 Nexa에 예제 자료를 등록하고 `data/live-smoke-results.json`에 기록합니다. 새 버전 테스트는 아래처럼 명시적으로 실행하며 JSON 결과를 표준 출력으로 내보냅니다.

```powershell
$env:NEXA_LIVE_VERSION_SMOKE = '1'
.\.runtime\bun\bun.exe --no-install tests/version-live-smoke.ts
Remove-Item Env:NEXA_LIVE_VERSION_SMOKE
```

## 기존 화면·운영 검증 기록

- 실제 브라우저에서 한국어 답변, 보드 필터, 코드 검색, 원문 줄 강조, 자료·작업 목록, 관리자 키 누락 오류를 확인했습니다. 요청 취소 후 입력도 정상 복구됐습니다.
- 데스크톱·390px 화면을 시각적으로 확인했고 320px에서도 가로 넘침이 없었습니다. 브라우저 콘솔 오류·경고는 0개였습니다. 인증된 업로드·삭제는 HTTP 통합 테스트로 검증했습니다.
- 모델·Qdrant·API 종료 후 다시 실행해 소스 2개·문서 5개·청크 6개와 벡터가 유지됨을 확인했습니다. 재시작 후 실제 질의 6개도 통과했습니다.

## 추가 검증이 필요한 항목

회사망에서 GitHub Release/LFS 대상 도메인 접근, NVIDIA/VC++ 런타임, A4000 메모리 사용량, 실제 보드 문서 정답 세트, 수만 파일의 색인 시간, 동시 사용자 대기 시간, 장시간 운영·디스크 장애 복구는 별도 검증 대상입니다. 깨끗한 Windows PC의 처음부터 설치, 운영체제 차원의 외부 통신 차단 검증은 수행하지 않았습니다.

임베딩 캐시는 같은 모델·입력의 재사용을 위해 원문 스냅샷 정리와 별도로 유지됩니다. 서로 다른 내용이 지속적으로 들어오는 장기 운영에는 캐시 용량·보관 정책이 추가로 필요합니다.
